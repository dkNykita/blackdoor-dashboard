BUG REPORT: Quoting an @param default embeds the literal quote characters into the value

Tags: script

Current behavior:
`# @param name "desc" default="VALUE"` (quoting VALUE) makes get_param() return the quote characters as part of the string. `get_param("blocks", "10")` then returns the 4-char string `"10"` (quotes included), not `10`. `int()` on that throws `Cannot convert '"10"' to int.`. The docs show the default unquoted (`default=VALUE`), but nothing warns that quoting it anyway silently corrupts the value instead of erroring or auto-stripping.

Expected behavior:
Either strip surrounding quotes from a quoted default (`default="10"` == `default=10`), or reject it with a clear parse error - not silently embed the quotes into the runtime value.

Process description:
Hit live on a new script's first run: crashed on its 2nd line with `Cannot convert '"10"' to int.`, from `int(get_param("blocks", "10"))` fed by `default="10"`. Two existing modules here already defensively strip quotes from param values with `.replace("\"", "").trim()` - this exact quirk was apparently already known project-side, just not identified as a general @param issue until now.

Steps to reproduce:
1. `# @param n "a number" default="5"`
2. `var x = int(get_param("n", "5"))`
3. Run with no arg passed for `n`.
4. Result: `Cannot convert '"5"' to int.` - value is the 3-char string `"5"` (quotes included), not `5`.
5. Removing the quotes (`default=5`) fixes it.

Sources:
- Official documentation/1.1.1/editor_documentation.txt, PARAMETERS section: shows `default=VALUE` unquoted as the only documented form.
- Confirmed live via a script crash and an isolated re-test with quotes removed.
- This project's field_notes.txt/CLAUDE.md carry the full writeup and a fix applied across 28 test scripts (23 declarations, 32 call sites, 2026-09-14).
