BUG REPORT: @param defaults leak their comment syntax (quotes, type) into get_param(), not the fallback

Tags: script

Current behavior:
When `@param name "desc" default=VALUE` exists and no runtime arg is passed, get_param(name, fallback) returns the @param's OWN default - not the inline `fallback` - typed/quoted exactly as written:
- `default="10"` (quoted) -> returns `"10"` WITH quotes embedded (4 chars), not `10`. `int()` on it throws `Cannot convert '"10"' to int.`.
- `default=10` (unquoted, numeric) -> returns a NUMBER, even if the inline fallback is a string (`get_param("n","10")`). `.replace()` on it throws `'number' has no method 'replace'`.
Return type/content depends purely on @param's own syntax, and can mismatch what the call site's fallback implies.

Expected behavior:
get_param() should return one consistent, documented type regardless of how the @param default is written - quotes shouldn't leak into the string, and a numeric default shouldn't silently switch the return type when the call site expects a string.

Process description:
Two successive live crashes on one script traced this: quoted default crashed with quotes embedded; removing the quotes crashed differently since the value became a real number. Two modules here already defensively str()+strip-quote param values - known piecemeal, not identified as one mechanism until now.

Steps to reproduce:
1. `@param n ... default="5"` + `int(get_param("n","5"))` -> crashes, quotes embedded.
2. Remove quotes (`default=5`) -> returns a real number, not "5" - a string method on it crashes.
3. An explicit runtime arg bypasses both - only surfaces via the default.

Sources:
- 1.1.1/editor_documentation.txt PARAMETERS section: `default=VALUE` shown unquoted, no type-coercion documented.
- Confirmed live via two successive crashes + isolated re-tests.
