BUG REPORT: download() denies /var/log files even for the confirmed owning, world-readable account

Tags: gameplay, script

Current behavior:
download(conn, path) returns {success: false, error: "permission denied"} for files under /var/log/*, even connected as the account `ls` shows as owner, with world-readable perms (-rw-r--r--). Failed for all 3 files in the dir, no exception.

Expected behavior:
Either download() should respect the permissions `ls` shows (succeed), or - if log files are intentionally scrub/delete-only - that should be documented for download()/read_file(). Nothing like this is mentioned officially.

Process description:
Connected as "anon42" against a target with /var/log containing auth.log, jobs.log, syslog (manually confirmed via `ls` - world-readable, owned by anon42). Our download() wrapper reported "Downloaded 0 files", no error - debug logging revealed permission denied on all 3. Same account against a DIFFERENT dir (/home/anon42) succeeded fully (6 files). Confirms the restriction is /var/log-specific, not account-related.

Steps to reproduce:
1. Log in to a target where you own (per `ls`) world-readable files in /var/log.
2. Call download(conn, "/var/log/some_file.log").
3. Result: permission denied, despite `ls` showing read access.
4. Compare: download() on a file OUTSIDE /var/log with the same account succeeds.

Sources:
- https://blackdoor.tools/api/ - download() entry has a success example, no permission model or /var/log restriction mentioned.
- The denial and its /var/log-specificity aren't documented anywhere - confirmed via live testing only.
