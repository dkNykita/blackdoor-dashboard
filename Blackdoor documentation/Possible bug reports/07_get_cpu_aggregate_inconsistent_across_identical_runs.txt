BUG REPORT: get_cpu()'s aggregate load behaves wildly inconsistently across identical script runs, causing unpredictable CPU-overload kills

Current behavior:
Running an IDENTICAL script, with identical data (same host_intel.txt), identical code, confirmed no other process running (`ps`/`jobs` empty, no scheduled daemons) - produces DRAMATICALLY different behavior between runs:
  - One run: the same operation (parsing a small local file) took ~197 real seconds, no crash.
  - Another run: the same operation crashed with "CPU overloaded" after only a few seconds.
  - Player's own observation: get_cpu() values jump unpredictably (e.g. 80/100-20-60-100-20 in quick succession), not smoothly rising/falling.
  - An isolated test (a bare script, NO imports, no state, just a while loop with 20x log()) crashed after ~13 iterations - proving even trivial, isolated load can trigger a crash independent of anything preceding it.

Expected behavior:
Either the CPU/tick model should be deterministic (same code + same data = same behavior), or there should be documentation explaining what actually influences get_cpu()'s reading (the aggregate "across all your processes" - but which processes exactly, over what time window, with what sampling/decay rate).

Process description:
This was the most extensive investigation of the whole session. We progressively ruled out: data volume in the file (a test with an empty file crashed at the same point), the number/size of imported modules (directly measured, negligible difference), external load on the real machine (out of scope), scheduled daemons (confirmed none active). We fixed real gaps in our own throttling (missing throttle() at function entry points, an accidentally-introduced throttle-call batching regression) - each fix pushed the crash point further out, but never eliminated it entirely. Widening safety margins (lower CPU thresholds, longer pauses) was tested and had NO effect on the crash point at all - only on how long it took to get there, a clean negative result.

UPDATE: a separate finding (see field_notes.txt) discovered that this codebase's assumption "connect()/scan()/download()/upload() cost 0 ticks" was wrong per the genuine official docs (web_api.txt) - those calls actually cost 1-50 real ticks each. That likely explains a meaningful share of unaccounted-for cost in OTHER parts of this codebase (refresh_status(), do_grab()) but does NOT explain the specific case documented here, since the crash reproduced with hostdata.bd's read_entries() - a function that makes no network-style calls at all, just local line-by-line parsing. The core inconsistency (identical local-only workload, wildly different outcomes) remains open.

Steps to reproduce:
1. Create a script that imports several modules (10+), then reads and parses a small local file (7-8 lines, a few dozen "tokens" to parse).
2. Run it repeatedly, with IDENTICAL data, with no other activity between attempts.
3. Observe: run time and outcome (success/crash) vary significantly between runs, even though the code and data are identical.
