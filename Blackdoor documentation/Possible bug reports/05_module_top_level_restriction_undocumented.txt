BUG REPORT: The import/module system itself is absent from official documentation, and its top-level statement restriction is undocumented

Current behavior:
A module (a file imported via `import "path" as alias`) may only have the following at its top level: function definitions, imports, or a `var` assigned a call-free (purely literal) value. Writing something like `var x = some_function()` at a module's top level is rejected with a PARSE error ("Module '...' has a statement at its top level that isn't a function definition, a constant `var` with a call-free value, or an import") - before the script even runs, not as a runtime error.

This restriction does NOT apply to a top-level SCRIPT (the main entry file) - a script routinely executes function calls in its own top-level statements without issue.

UPDATE after cross-checking the genuine official docs (Blackdoor documentation/Official documentation/, including the full web API reference web_api.txt at https://blackdoor.tools/api/): the `import` keyword and the entire module/multi-file-script system are not mentioned ANYWHERE in the official documentation set - not in web_api.txt (897 lines, the most comprehensive official source), not in api_quickref.txt, not in editor_documentation.txt. This is a bigger gap than originally filed: it's not just this one restriction that's undocumented, the whole import/module feature appears to be entirely unofficial/undocumented, something players apparently have to discover through experimentation or community knowledge alone.

Expected behavior:
Either a module should support the same expressiveness as a script (for consistency), or - at minimum - the `import` keyword and module system should be documented somewhere official, including this top-level restriction and how modules differ from scripts.

Process description:
We ran into the top-level restriction while attempting an "eager" initialization of a cached value at module level (`var _tick_rate_cache = _read_tick_rate_from_config()`), motivated by wanting to read a config value only once per script run instead of repeatedly. We expected it to work the same as in a top-level script. The script didn't run at all - straight to a parse error. Only afterward, while compiling this report, did we discover that `import` itself isn't documented anywhere official at all.

Steps to reproduce:
1. Create a module (a file imported via `import`) containing:
   func get_value():
       return 5
   var cached = get_value()
2. Import this module from any script.
3. Result: parse error "Module '...' has a statement at its top level that isn't a function definition, a constant `var` with a call-free value, or an import" - the script doesn't run at all.
4. The same pattern (`var x = some_function()`) directly in a TOP-LEVEL SCRIPT (not a module) works fine.
5. Search web_api.txt / api_quickref.txt / editor_documentation.txt for "import" - no matches in any of them.
