BUG REPORT: A module's top-level statement restriction is undocumented and inconsistent with top-level scripts

Tags: script

Current behavior:
A module (imported via `import "path" as alias`) may only have function defs, imports, or a `var` assigned a call-free (literal) value at its top level. `var x = some_function()` at a module's top level is rejected with a PARSE error before the script even runs.

This does NOT apply to a top-level SCRIPT (main entry file) - a script freely calls functions in its own top-level statements.

`import` itself IS documented (`import "utils"`, `import "utils" as u`), but nothing describes this module/script asymmetry or the call-free-value restriction.

Expected behavior:
Either a module should support the same expressiveness as a script, or this restriction should be documented alongside the existing `import` entry.

Process description:
Ran into this attempting an "eager" cache init at module level (`var _tick_rate_cache = _read_tick_rate_from_config()`), to read a config value once per run. Expected it to work like a top-level script - nothing in the `import` docs suggested otherwise. The script didn't run at all.

Steps to reproduce:
1. Create a module containing:
   func get_value():
       return 5
   var cached = get_value()
2. Import it from any script.
3. Result: parse error, script doesn't run at all.
4. The same pattern directly in a TOP-LEVEL SCRIPT (not a module) works fine.

Sources:
- `import` documented in the in-editor scripting reference (FUNCTIONS section): `import "utils"`, `import "utils" as u`. No mention of the top-level restriction or module/script asymmetry there or anywhere else checked.
- The restriction itself: confirmed only via the engine's own live parse error this session.
