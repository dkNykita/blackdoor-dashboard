BUG REPORT: Module top-level statement restrictions are undocumented and inconsistent with top-level scripts

Current behavior:
A module (a file imported via `import "path" as alias`) may only have the following at its top level: function definitions, imports, or a `var` assigned a call-free (purely literal) value. Writing something like `var x = some_function()` at a module's top level is rejected with a PARSE error ("Module '...' has a statement at its top level that isn't a function definition, a constant `var` with a call-free value, or an import") - before the script even runs, not as a runtime error.

This restriction does NOT apply to a top-level SCRIPT (the main entry file) - a script routinely executes function calls in its own top-level statements (calling API functions, helper functions, etc.) without issue.

Expected behavior:
Either a module should support the same expressiveness as a script (for consistency), or this restriction should be clearly documented next to `import` in api_documentation.txt - currently there's no mention of it anywhere, and the error message is the only way to discover it (and only after attempting it, not in advance).

Process description:
We ran into this while attempting an "eager" initialization of a cached value at module level (`var _tick_rate_cache = _read_tick_rate_from_config()`), motivated by wanting to read a config value only once per script run instead of repeatedly. We expected it to work the same as in a top-level script. The script didn't run at all - straight to a parse error.

Steps to reproduce:
1. Create a module (a file imported via `import`) containing:
   func get_value():
       return 5
   var cached = get_value()
2. Import this module from any script.
3. Result: parse error "Module '...' has a statement at its top level that isn't a function definition, a constant `var` with a call-free value, or an import" - the script doesn't run at all.
4. The same pattern (`var x = some_function()`) directly in a TOP-LEVEL SCRIPT (not a module) works fine.
