BUG REPORT: connect().success does not mean authenticated - undocumented in api_documentation.txt (inconsistency between doc sources)

Current behavior:
connect(target, port) returns {success: true, user: "", ...} even for WRONG or uncracked credentials - success:true only means "the port was reachable", not "login succeeded". The only reliable way to confirm actual authentication is checking user != "".

This behavior IS documented in documentation_from_editor.txt (the in-editor reference), but is NOT mentioned in api_documentation.txt (the main/official reference), where connect() reads as if success:true were sufficient confirmation of a successful connection.

Expected behavior:
api_documentation.txt should carry the same warning as documentation_from_editor.txt - otherwise it's a trap for anyone relying only on the "official" reference: they'll write `if conn.success: ...` and assume authentication, while actually they've only reached a reachable port without any password verification.

Process description:
We found this gap unchecked everywhere in our own codebase - net.bd's connect_or_raise() and every caller (do_grab/do_scrub_log/do_raw_cleanup/do_escalate, menu.bd's refresh_status()) only checked .success. Discovered while reading documentation_from_editor.txt, not api_documentation.txt - had we relied only on the "official" reference, we would never have caught this gap ourselves, only via a live test with a wrong password.

Steps to reproduce:
1. Call connect("wrong_account@target", 22) with a wrong/uncracked password.
2. Result: {success: true, user: "", ...} - looks like success, but user is empty.
3. Compare with api_documentation.txt's description of connect() - there's no mention anywhere of needing to check user != "".
