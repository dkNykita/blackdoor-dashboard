BUG REPORT: connect().success does not mean authenticated - the official web API reference's own example doesn't flag this

Tags: script

Current behavior:
connect(target, port) returns {success: true, user: "", ...} even for WRONG/uncracked credentials - success:true only means the port was reachable, not that login succeeded. The only reliable check is user != "".

This IS documented in the in-editor `help api` reference, but NOT flagged in the web API site's (blackdoor.tools/api) own connect() entry - its example shows only the successful-auth case, no warning.

Expected behavior:
The web reference's connect() entry should carry the same warning the in-editor one has - a player reading only the web reference (the more prominent one) will write `if conn.success:` and wrongly assume authentication.

Process description:
Found this gap unchecked everywhere in our own codebase (connect_or_raise() and every caller only checked .success). Discovered via the in-editor reference, not the web one - relying only on the web reference, we'd never have caught it ourselves, only via a live test with a wrong password.

Steps to reproduce:
1. Call connect("wrong_account@target", 22) with a wrong/uncracked password.
2. Result: {success: true, user: "", ...} - looks like success, user is empty.
3. Compare with the web reference's connect() example - only shows a successful case, no user != "" warning.

Sources:
- In-editor `help api`: "`success` only means the network connection opened (port reachable) - wrong credentials still return success:true with `user` empty... check `user != ""` to confirm login actually worked."
- blackdoor.tools/api/ - connect() example shows only {id, success: true, user: "root", ...}, no warning.
