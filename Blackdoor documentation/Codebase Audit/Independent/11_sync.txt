CODEBASE AUDIT - INDEPENDENT PASS
File: utils/sync.bd (101 lines, 1 function)
============================================================

do_sync(nu, uc, uhd)
  Evidence: 1 call site (menu.bd startup, once per run).
  Nested calls: uhd.read_entries(), uhd.find_entry(), uhd.write_
  entries(), uc.read_credentials(), nu.throttle() (per known_hosts
  line, per credentials-derived host, per wordlist line, per credential
  password), read_local(), local_mkdir(), save(), store().
  Purpose: three independent local-file maintenance passes in one
  function - known_hosts merge into host_intel.txt, credentials-to-
  Network-tab backfill, and wordlist dedup-append. This is the ONE
  legitimate caller of hostdata.bd's full read_entries()/write_entries()
  and creds.bd's full read_credentials() - it genuinely needs every
  host's data at once to merge, not one host's.
  Alternatives:
    - Split into 3 separate functions (sync_hosts()/sync_network_tab()/
      sync_wordlist()) instead of one 101-line function doing all
      three: would improve readability and let a caller run just one
      piece if ever needed, at zero performance difference (same total
      work either way) - a pure maintainability refactor, not a
      performance one.
    - The wordlist-building loop re-scans `existing_lines` (via
      .contains()) once per credential to dedup - for a small wordlist
      this is fine; if wordlists/common.txt grows very large across many
      sessions, a dict/set-keyed dedup check would be faster than a
      linear .contains() scan per password, though BDScript has no
      confirmed Set type - would need a dict with dummy values as a
      workaround. Worth revisiting only if wordlist size becomes a
      practical problem (the file's own comment already flags this
      exact loop as having crashed once from unpaced growth, since
      fixed with per-line throttling - the dedup approach itself was
      never the issue, just the missing pacing).
