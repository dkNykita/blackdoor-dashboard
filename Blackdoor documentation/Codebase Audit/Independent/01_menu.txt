Import chain (line 77-125, 11 modules + sleep(1) after each)
  Evidence: this IS the only importer of all 11 utils/*.bd modules in
  the whole codebase - every other module takes `nu` (and sometimes
  `uc`/`uhd`) as a plain parameter instead of importing independently,
  specifically to avoid the confirmed "import isn't cached, re-executes
  the whole file" cost multiplying across modules.
  Purpose: single, deliberate import point with real sleep(1) pacing
  between each - directly matches field_notes.txt's confirmed finding
  that importing costs ticks proportional to a module's total line
  count (not just its top-level statements) and that back-to-back
  imports alone can overload a script before its own logic even starts.
  Alternatives: none - this is already the minimal-import-count,
  maximally-paced shape given BDScript's confirmed no-import-caching
  behavior.

startup_t0 / debug instrumentation (line 77, then debug_time() calls
throughout)
  Purpose: bookends every startup phase with get_unix_time() (0-cost)
  to measure real wall-clock cost per phase instead of guessing - a
  genuinely useful diagnostic tool, currently always-on (see net.bd's
  debug_enabled() audit - hardcoded true).
  Alternatives: the file's own comment says "Remove once the real
  bottleneck is identified" - given the bottleneck is still not fully
  identified (ongoing investigation), removing this now would be
  premature; keep it until the investigation concludes.

state dict (line 140-182, 20 fields)
  Purpose: single dict replacing ~20 separate top-level vars, since
  every field needs threading into/out of utils/dashboard.bd's
  functions as one parameter (this codebase never trusts implicit
  mutation-by-reference across a call). Multi-line literal now that
  v1.1.1 allows it - per-field comments live inline instead of a
  separate block above.
  Alternatives: none - this is already the documented, deliberate fix
  for a real language constraint (module-top-level-var caution).

Target resolution + target_is_own_ip (line 194-207)
  Purpose: resolves the @param target, falling back to the mission
  target, then to the player's own IP if neither is set - and
  precomputes target_is_own_ip once so every subsequent probe_
  firewall()/whois()/connect() call can skip itself cleanly instead of
  attempt-and-catch every time. Efficient, correct.
  Alternatives: none.

Startup hydration: ONE get_entry() call (line 217-224)
  Purpose: hydrates 6 state fields from a SINGLE uhd.get_entry() call
  instead of 6 separate get_*() calls - the file's own comment already
  reasons about why (each get_*() is its own full lookup pass). This
  now benefits automatically from get_entry()'s targeted-lookup fix.
  Alternatives: none - already optimal given get_entry()'s current
  implementation.

Dispatch loop (line 240-415): print_dashboard() -> throttle -> menu ->
prompt -> 8 branches (0/r/s/t/1-7)
  Evidence: every branch that changes `state` reassigns it from the
  called function's return value (never trusts mutation-by-reference) -
  consistent discipline throughout.
  Purpose: single long if/elif dispatch instead of a lookup table -
  reasonable given BDScript has no confirmed first-class dispatch-table
  idiom demonstrated anywhere else in this codebase, and the number of
  actions (8) is small enough that a table wouldn't meaningfully clarify
  anything.
  Alternatives:
    - Choice "t" (change target) duplicates the SAME 6-field
      re-hydration pattern as the initial startup hydration (line
      306-312) - a small, low-risk opportunity to factor both into one
      shared "hydrate state from a fresh get_entry() result" helper
      (would live naturally in utils/dashboard.bd alongside refresh_
      status()/mark_cracked()). Purely a DRY win, zero performance
      difference either way.
    - Choices "3"/"4"/"5"/"6" each independently wrap their action call
      in the same try/catch-log(str(e))-amber pattern for the
      documented trace_hopeless() raise - already about as minimal as
      that repetition can be without a shared "try-and-log" helper,
      which would need to accept an arbitrary callable + its args
      (possible via BDScript's confirmed function-as-value support, per
      crack.bd's callback pattern) - a real, modest DRY opportunity, low
      priority given how small each individual repetition already is.
