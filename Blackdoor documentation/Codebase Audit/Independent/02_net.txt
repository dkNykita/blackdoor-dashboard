debug_enabled()
  Location: line 30-31. Evidence: ~7 call sites (every module's debug
  gate checks). Nested calls: none, returns a hardcoded `true`.
  Purpose: single on/off switch for the "DEBUG TIME:" checkpoint
  logging used throughout the codebase. Currently hardcoded to `true`,
  i.e. NOT actually toggleable at runtime despite the name and the
  comment describing it as a debugging on/off switch - this is a real
  finding: it's always on in every current run, meaning every debug_
  time() call's guard check always passes and the string-concat/log()
  cost is always paid. If a genuinely quiet, non-debug run of this
  codebase is ever wanted, this needs to be flipped to `false` and
  re-verified that guarded call sites (the ones with `if nu.debug_
  enabled():` around string-concat, not just around debug_time() itself)
  correctly skip their cost too.
  Alternatives: read this from a config value (e.g. blackdoor.conf) like
  local_tick_rate() does, instead of a hardcoded literal - would let a
  player toggle it without editing source, at the cost of a file-read
  per check unless cached. Given this function is called ~7 times per
  run (not hundreds), the read cost would be trivial - a reasonable
  small improvement if runtime toggling is ever wanted.

local_tick_rate()
  Location: line 79-98. Evidence: 1 call site (menu.bd, informational
  startup log only).
  Nested calls: read_local(), string split/starts_with/replace/int().
  Purpose: reads `~/.config/blackdoor.conf`'s `tick_speed=N` line since
  no API call reports the player's OWN tier directly (server_specs(conn)

cpu_guard_conservative() / cpu_guard_fast()
  Location: line 108-114. Evidence: extremely high-traffic - ~34 and
  ~41 call sites respectively (every throttle() call in the codebase
  picks one of these two).
  Nested calls: none, return hardcoded 50 / 80.
  Purpose: named CPU thresholds instead of bare numbers at every
  throttle() call site - lets the whole codebase's pacing behavior be
  retuned from 2 return values. The two-threshold split's original
  intent (light vs. costly calls) has drifted in practice - see
  Integrated pass for the documented history on this.
  Alternatives: collapse to a single threshold, or rename to reflect
  the ACTUAL distinction now in play (connection/trace risk, not call
  weight) - the file's own historical comments already flag this as an
  open naming/consolidation task, not yet acted on.

throttle(threshold)
  Location: line 165-168. Evidence: the single highest-traffic function
  in the ENTIRE codebase - ~89 call sites.
  Nested calls: sleep(), get_cpu() (in the while condition).
  Purpose: the one shared CPU-safety primitive everything else builds
  on - `sleep(log_pace())` then poll-and-wait until get_cpu() clears
  threshold. Simple, correct shape for what it does.
  Alternatives:
    - A shorter retry interval than log_pace()=1s: tried historically
      (see file's own ABANDONED comment, lines 150-164) and crashed the
      script every time - not viable with current understanding.
    - Skip the wait entirely if get_cpu() already reads under threshold
      on first check (equivalent to what this function already does,
      since the while condition is checked before any extra sleep
      beyond the unconditional first one) - already effectively the
      current behavior via the initial `sleep(log_pace())` + immediate
      while-check.
    - This is also the function whose OWN cost is now understood to be
      non-negligible (get_cpu() itself observed to add load, not the
      documented 0-tick primitive) - see Integrated pass for the full
      chain of live evidence. No concrete fix has been found yet; this
      remains the central open question of the whole investigation.

FILE-LEVEL OBSERVATION: unlike most other modules in this codebase
(which lean on field_notes.txt as the primary historical record and
keep their own comments relatively short), utils/net.bd embeds several
large historical narratives directly in its own comments (the CPU-
tier-auto-scaling abandonment, the throttle-interval-shortening
abandonment, the cpu_guard_*() naming drift). This is more
self-contained/robust (survives even if field_notes.txt is ever lost or
badly edited) but creates a real risk of the two sources drifting apart
over time - worth deciding, as a house style choice, whether net.bd's
approach or the rest of the codebase's approach should be the standard
going forward, rather than leaving it inconsistent by file.
