throttle(threshold)
  field_notes.txt history: this is the single most load-bearing function
  in the ENTIRE investigation. CONFIRMED via direct player observation:
  get_cpu() itself adds load (contradicts its documented "0 ticks" cost)
  - meaning this function's own `while get_cpu() > threshold: sleep(...)`
  retry loop is partly self-defeating, each poll nudging load back up.
  This explains the field's own historical ABANDONED-shorter-interval
  finding (lines 150-164) MORE precisely than that comment could at the
  time it was written: a shorter retry interval doesn't just fail to
  help because "get_cpu() needs real time to decay" (the original,
  correct-but-incomplete explanation) - it also means MORE frequent
  get_cpu() calls per unit time, each one itself adding load, compounding
  the problem. Three separate live experiments this session directly
  manipulated the NUMBER of throttle() calls around this function's own
  cost (add one, remove one, add one elsewhere) - 2 made the real crash
  happen sooner, 1 had zero effect - CONFIRMED "throttle-count/placement
  tuning" is an exhausted direction for now (see field_notes.txt STATUS
  note), NOT because throttle() itself is wrong, but because we don't yet
  have a working theory for what a genuine FIX to this function would
  look like beyond "call it less/differently," which has now been tried
  three ways.
